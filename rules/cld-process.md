# 폐루프 개발 프로세스 (closed-loop-dev)

이 저장소는 폐루프로 개발한다. 문서 셋이 세션 사이의 기억이고, 세션 두 종류가 번갈아 돈다.

## 문서 셋 — 무엇이 무엇의 SSOT 인가

| 문서 | SSOT | 누가 고치나 |
|---|---|---|
| 마스터 플랜 `{{MASTER_PLAN}}` | 목표 · 완료 기준 · Phase 순서 · 게이트 · 결정 | 계획 세션 · 검증 세션(상태 칸 · 결정) |
| 세션 프롬프트 `{{SESSION_PROMPTS}}` | 세션 단위로 자른 실행 지시 | 계획 세션 · 검증 세션(«이번 세션») |
| 인수인계 `{{HANDOVER}}` | 세션 간 기억 — 깨지기 쉬운 것 · 되돌리는 법 · 믿지 말 것 · 다음 사람에게 | 구현 세션(항목 신설) · 검증 세션(항목 보강) |
| `{{TASKS_DIR}}/` | 과제 단위 사실 · 트리거 | 누구나(인덱스와 같은 변경에서) |
| `{{CHANGELOG}}` | 출하된 차이 | 구현 세션 · 검증 세션(검증 한 줄) |

## 루프 — 한 바퀴

1. **계획**: 마스터 플랜에 목표 · 완료 기준 · Phase 표를 둔다. Phase 마다 세션 프롬프트 절을 쓴다(스킬 `cld-plan`).
2. **프롬프트**: 다음 Phase 의 프롬프트를 하네스로 조립해 사용자에게 준다(스킬 `cld-prompt`). 메시지는 «대상: …» 한 줄로 시작하고, 권고 모드를 근거와 함께 먼저 적는다.
3. **구현 세션**(독립 세션): 인수인계부터 읽고, 한 Phase(또는 한 커밋 단계)만 한다. 게이트를 돌리고 인수인계 맨 위에 항목을 넣는다. 커밋은 사용자가 한다(스킬 `cld-implement` · `cld-handover`).
4. **독립 검증 세션**(구현과 다른 세션): 사용자가 «<커밋> 완료했어» 라고 하면 그 커밋을 깨끗한 트리에서 다시 검증하고, 결과를 인수인계 · CHANGELOG · 과제에 적는다(스킬 `cld-verify`).
5. **폐루프**: 검증 세션이 마스터 플랜 상태 칸 · 결정 · 다음 Phase 의 «이번 세션» 을 고치고, 사용자 결정이 필요한 것을 묻는다. 요청을 받으면 다음 프롬프트를 만든다(스킬 `cld-close`) → 2 로 돌아간다.

## 규칙

- **한 세션 = 한 Phase(또는 한 커밋 단계).** 세션은 기억을 물려받지 못한다. 기억은 문서 셋에만 있다.
- **Phase 를 늘리지 않는다.** 후속은 다음 예정 단계에 합치기부터 검토한다. 떼야 하면 이유 한 문장과 함께 먼저 묻는다.
- **프롬프트는 짧게.** 끝난 단계 · 이력 · 일화 · 중복을 뺀다. 머리는 열 줄 안쪽이다.
- **모드 권고를 근거와 먼저**(🔴 울트라코드 · 🟡 검토 워크플로 한 번 · 🟢 MAX — 기본). 모드는 사용자가 정한다. 🔴 · 🟡 에만 다중 에이전트 블록을 붙인다.
- **결정은 사용자 몫이다.** 결정 기록(마스터 플랜 §4)에 있는 것은 다시 묻지 않는다. 결정 밖 설계만 먼저 묻는다. 결정은 날짜와 함께 적는다.
- **인수인계는 네 칸이다.** 빈 칸은 «없음». 한 쪽을 넘지 않는다. «완료했다 · 측정했다» 는 인수인계가 아니다.
- **검증은 구현과 다른 세션이 한다.** 구현 세션의 자기 검증(검토 워크플로)은 독립 검증을 대신하지 않는다.
- **검증이 찾은 결함은 이월 목록으로.** 인수인계 «다음 사람에게» 끝의 «독립 검증» 항목이 SSOT 다. 다음 커밋 첫머리가 싣는다. 🔴 은 과제로 떼고 사용자에게 순서를 묻는다.
- **사용자가 돌리는 긴 시험은 넘기기 전에 점검한다.** 트리거 조건 · 판정의 공허 조건(아무것도 안 봐도 PASS 하는가)을 먼저 본다. 재실행을 반복하지 않는다.
