# 마스터 플랜과 Phase 나누기

문서 경로는 `.cld/config.toml` 의 `[docs]` 다. 먼저 `python .cld/harness/cld.py status` 로 지금 상태를 본다.

## 1. 계획을 쓰기 전에

- 저장소의 README · docs · 규칙을 읽고 프로젝트를 요약한다. 현황은 코드로 확인한 것만 «검증된 현황» 에 적는다(날짜 · 커밋).
- 사용자가 이미 정한 것은 결정 기록(§4)에 날짜와 함께 옮긴다. 다시 묻지 않는다.
- 사용자에게 물을 것은 목적 · 완료 기준 · 범위 밖(하지 않는 것) · 바꿀 수 없는 제약 넷이다. 묻는 것마다 선택지와 권고를 붙인다.

## 2. 완료 기준

- 기준마다 측정 방법을 적는다. 측정할 수 없는 기준은 기준이 아니다.
- «끄고도 출하 가능» 을 안전장치로 둔다. 근거가 안 닫힌 기능은 끈 채로 출하한다.

## 3. Phase 나누기 원칙

- **한 Phase = 독립 세션 하나.** 크면 «커밋 단계» 로 나누고(예: P3 C1 · C2), 표의 «세션» 칸에 수를 적는다. 표 한 줄이 규모를 감추지 않게 한다.
- **독립 검증이 가능한 단위**로 자른다. 커밋마다 게이트가 무엇을 증명하는지 한 문장으로 말할 수 있어야 한다.
- **값이 바뀌는 커밋과 안 바뀌는 커밋을 섞지 않는다.** 값 불변 커밋은 게이트가 «차이 0» 으로 증명한다. 값이 바뀌는 커밋은 기준선을 다시 뜨고 그 차이를 설명한다.
- **위험한 것을 앞으로.** 풀빌드 · 배포 경로 검증이 마지막 한 곳뿐이면 앞으로 당긴다.
- **순번이 순서다.** 이름은 한 번 정하면 바꾸지 않는다(과거 기록이 이름을 가리킨다). 순서를 바꾸면 순번만 고치고 근거를 한 줄 적는다.
- **Phase 를 늘리지 않는다.** 후속은 다음 예정 단계에 합치기부터 검토한다.

## 4. 게이트

- 공통 게이트(커밋마다)를 §2.1 표에 적는다. 게이트마다 무엇을 보고 **무엇을 못 보는지** 함께 적는다.
- `.cld/config.toml` 의 `[[gates]]` 에 명령을 인자 목록으로 넣는다. 같은 group 은 동시에 돈다(자원이 겹치지 않는 것만 같은 group 에).
- 게이트가 원리상 못 보는 것(설치본 · 배포 · 화면 · 외부 장비)은 Phase 절의 «전용 시험» 에 적는다.

## 5. 세션 프롬프트 절 만들기

Phase 마다 세션 프롬프트 문서에 절을 하나 둔다(형식은 그 문서의 `## P1.` 예시).

````
## <id>. <제목>

권고 모드: 🟢 — <근거: 기준 ⓐ 변경면 ⓑ 게이트가 못 보는 위험 ⓒ 되돌리기 어려움 ⓓ 독립 질문 중 무엇>

```cld-head
(선택 — 없으면 하네스가 기본 머리를 만든다. 열 줄 안쪽)
```

```cld-body
(«■ 이번 세션» · 물을 것 ⓪ · 할 일 · 하지 않는 것 · 남은 Phase · 전용 게이트)
```
````

- 울트라코드 영문 낱말은 🔴 절의 머리에만(하네스가 넣는다). 🟢 · 🟡 절의 어디에도 쓰지 않는다.
- 만든 뒤 `python .cld/harness/cld.py prompt build <id> --out <스크래치>/p.txt` 로 조립이 되는지 본다.

## 6. 끝낼 때

- 마스터 플랜 변경 이력 · 결정 기록을 같은 변경에서 고친다.
- 사용자에게: 계획 요약(표) · 물을 것 · 첫 Phase 의 권고 모드 · 커밋 명령과 메시지 초안. 첫 프롬프트는 요청을 받으면 `cld-prompt` 로 준다.
