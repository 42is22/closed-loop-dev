## 0. 쓰는 법

1. **프롬프트는 하네스가 조립한다.** `python .cld/harness/cld.py prompt build <Phase> --out <파일>` 이 머리 + 공통 블록 + Phase 블록(+ 🔴 · 🟡 면 다중 에이전트 블록)을 잇는다. 사람은 그 결과를 새 세션에 통째로 붙인다. 한 세션에 한 Phase(또는 한 커밋 단계)다.
2. **짧게 둔다.** 끝난 단계 · 이력 · 일화 · 중복은 넣지 않는다. 머리는 열 줄 안쪽이다(하네스가 막는다). 🟢 세션 기준 약 120줄을 목표로 한다.
3. **권고 모드를 먼저 적는다.** Phase 절마다 `권고 모드: 🔴|🟡|🟢` 한 줄과 근거를 둔다. 모드는 사용자가 정한다. 기본은 🟢 MAX 다.
   - 🔴 울트라코드: 모든 실질 작업을 워크플로로 돌린다. 머리 첫 줄에 울트라코드 영문 낱말이 들어간다(하네스가 넣는다).
   - 🟡 검토 워크플로 한 번: 구현은 MAX, 구현 뒤 검토에서만 워크플로를 한 번 돌린다.
   - 🟢 MAX: 워크플로 없이.
   - 기준: ⓐ 변경면이 넓다 ⓑ 게이트가 원리상 못 보는 위험이 있다 ⓒ 현장 · 사용자에게 바로 닿거나 되돌리기 어렵다 ⓓ 독립 질문이 많다. 셋 이상이면 🔴, ⓑ 가 있고 변경면이 중간이면 🟡, 나머지는 🟢 다.
   - 🟢 · 🟡 프롬프트에는 울트라코드 영문 낱말을 쓰지 않는다(그 낱말이 모드를 켠다 — 하네스가 막는다).
4. **«이번 세션» 은 검증 세션이 고친다.** 구현 세션이 끝나고 독립 검증이 끝나면, 검증 세션이 다음 Phase 절의 «■ 이번 세션» 에 검증이 찾은 이월(인수인계 «다음 사람에게» 의 검증 항목)을 싣고 끝난 항목을 걷는다.
5. 끝낼 때 다음 Phase 프롬프트를 미리 만들지 않는다. 다음 프롬프트는 검증 세션이 만든다(폐루프).

## 1. 공통 블록

⚠ 여기를 고치면 모든 Phase 프롬프트가 바뀐다. 한 번만 고친다.

```cld-common
{{PROJECT}} 의 한 Phase 를 수행한다. 계획서는 {{MASTER_PLAN}} 이고, 이 세션은 그중 한 단계만 한다.

■ 먼저 읽을 것 (순서대로)
  1. 🔴 {{HANDOVER}} — 앞선 세션이 남긴 인수인계. «믿지 말 것» 과 «다음 사람에게» 는 전부 읽는다.
  2. CLAUDE.md 와 .claude/rules/*.md (특히 cld-process · cld-git)
  3. {{MASTER_PLAN}} — §0 완료 기준 · §2 이 Phase 행 · §4 결정 기록. 결정은 다시 묻지 않는다. 결정 밖 설계만 먼저 묻는다.
  4. {{TASKS_DIR}}/README.md «무엇을 기다리는가» — 이 세션이 확보하는 자원이 누군가의 트리거인가

■ 브랜치 · 버전 · 커밋 이름
  브랜치 · 버전 규약은 .claude/rules/cld-git.md 를 따른다. 산출은 {{CHANGELOG}} [Unreleased] 에 쌓는다.
  커밋 제목은 «<type>(<scope>): <Phase> C<번호> — …» 꼴이다(Conventional Commits).

■ 게이트 (커밋마다)
  python .cld/harness/cld.py gates run --out <저장소 밖 스크래치> — 전부 PASS 여야 한다. 정의는 .cld/config.toml [[gates]].
  ⚠ 게이트가 원리상 못 보는 것(설치 · 배포 경로 · 화면 · 외부 장비)은 이 커밋의 전용 시험을 더한다.

■ 규칙
  - 값이 안 바뀌어야 하는 커밋에서 게이트가 차이를 내면 멈추고 원인을 적는다. 기준선을 다시 뜨지 않는다.
  - 줄 번호는 낡는다. 이름으로 찾는다.
  - 결정이 필요하면 멈추고 묻는다. 묻는 것은 선택지 · 권고 · 근거 한 줄이다.

■ 하지 않는 것
  - git commit · push · tag 를 실행하지 않는다(커밋 메시지 초안 · 명령까지). 패키지 설치 · 제거를 실행하지 않는다(명령만 제시).
  - Phase 를 늘리지 않는다. 떼야 하면 이유 한 문장과 함께 먼저 묻는다.

■ 끝낼 때
  - 변경 파일 목록 · 게이트 결과 · Conventional Commits 커밋 메시지 초안을 낸다.
  - 마스터 플랜의 이 Phase 행과 {{CHANGELOG}} [Unreleased] 를 같은 변경에서 고친다.
  - 🔴 인수인계 맨 위에 이 커밋 항목을 넣는다(python .cld/harness/cld.py handover new · check): 깨지기 쉬운 것 / 되돌리는 법 / 믿지 말 것 / 다음 사람에게.
    빈 칸은 «없음» 이다. 한 쪽을 넘지 않는다. «완료했다» 는 적지 않고, 다음 사람의 행동을 바꾸는 것만 적는다.
  - 새 사실은 docs/ · {{TASKS_DIR}}/ 에 남긴다.
  - 끝내지 못하면 인수인계에 멈춘 자리와 남은 일을 적는다. 다음 세션이 잇는다.
  - 🔴 · 🟡 세션은 이 블록 뒤에 «다중 에이전트 운용» 이 붙는다. 붙지 않았으면 MAX 로 돈다.
```

## M. 다중 에이전트 운용 — 🔴 · 🟡 세션에만 붙는다

```cld-multi
■ 다중 에이전트 운용 — 🔴 울트라코드 · 🟡 검토 워크플로 한 번
  목적: 게이트가 원리상 못 보는 결함을 커밋 전에 찾는다. 양보다 독립된 관점이 찾는다.
  🔴 울트라코드: 모든 실질 작업을 워크플로로 돌린다.
  🟡 검토 워크플로 한 번: 구현은 MAX 로 하고, 구현 뒤 검토에서만 워크플로를 한 번 돌린다(관점 넷 ~ 여섯 + 발견마다 반증 · 에이전트 10 안팎).
  나누는 것(읽기 전용 에이전트): 착수 전 이해 · 소비자 전수 스윕 · diff 검토 · 발견 반증 · 끝내기 전 «무엇을 안 봤나» 비평.
  나누지 않는 것(메인 루프): 파일 편집 · 게이트 · 인수인계 · 커밋 메시지. 같은 파일을 두 에이전트가 고치지 않는다.
  🔴 에이전트는 이 프롬프트를 못 본다(CLAUDE.md 와 .claude/rules 만 받는다). 에이전트 프롬프트마다 공통 규칙을 넣는다 —
     python .cld/harness/cld.py verify scope <base> <head> 가 규칙 문장을 낸다.
  흐름: ① 이해 ② 구현(메인 루프) ③ 관점별 검토 + 발견마다 반증 ④ 게이트 → 고침 → 고친 곳만 ③ 다시 ⑤ «무엇을 안 봤나» 비평 → 인수인계.
  검토 관점에 둘을 꼭 둔다: «게이트가 타지 않는 입구»(스위치 · 설정 조각 · 도구 인자 · 설치 경로) · 값 불변 주장의 흔든 입력 대조.
  인수인계에 워크플로가 찾은 결함 수와 반증된 발견 수를 한 줄로 적는다.
```
